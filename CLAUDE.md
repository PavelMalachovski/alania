# CLAUDE.md

Продающий Telegram-бот (воронка) для эксперта Ланы: прогрев, презентация услуг,
запись на консультацию по слотам, заявки, рассылки и дожим-напоминания.

## Стек

- Python 3.12, **aiogram 3.x** (FSM, роутеры, middleware)
- SQLAlchemy 2.0 (async, `Mapped`/`mapped_column` style) + asyncpg
- PostgreSQL (Railway), в тестах — sqlite+aiosqlite
- Docker (`python:3.12-slim`), деплой на Railway (polling, не webhook)

## Запуск

```bash
pip install -r requirements.txt
# заполнить .env по образцу .env.example
python main.py
```

Обязательные env-переменные: `BOT_TOKEN`, `ADMIN_IDS`, `DATABASE_URL`.
`ADMIN_IDS` — список Telegram ID через запятую (`111,222`). Старый `ADMIN_ID`
(один id) поддерживается как fallback. `TZ=Europe/Prague`.

## Архитектура

- `main.py` — точка входа. Парсит `ADMIN_IDS`, вешает middleware, регистрирует
  глобальный `dp.errors()`, запускает фоновые задачи дожима (`followup_loop`)
  и проверки оплат (`payments_loop`, только если задан `LAVA_API_KEY`),
  прокидывает `admin_ids` в polling (доступны в хендлерах и фильтрах как
  workflow data — аргумент `admin_ids: list[int]`), так же `lava:
  LavaClient | None` (в хендлерах — с дефолтом `= None`: без ключа кнопки
  оплаты отвечают «оплата недоступна», а не падают).
- `lava.py` — `LavaClient` для `https://gate.lava.top` (ключ в заголовке
  `X-Api-Key`): `create_invoice(email, offer_id, currency)` →
  `POST /api/v2/invoice`, `invoice_status(id)` → `GET /api/v1/invoices/{id}`.
  `LavaError.email_invalid` — 400 с `details.email` (lava.top сам валидирует
  email): клиента просят ввести адрес заново. `OFFERS` — id офферов сессии,
  курса и игры из кабинета (`GET /api/v2/products?feedVisibility=ALL`: курс
  и игра там скрыты из витрины, без `ALL` их не видно). Цена — в оффере,
  бот шлёт только id и валюту (`RUB`/`EUR`).
- `payments.py` — автоподтверждение. Вебхуков нет (бот на polling без
  публичного адреса): `payments_pass` опрашивает неоплаченные счета —
  первый час на каждом проходе (`POLL_INTERVAL = 20` с), потом не чаще
  `SLOW_EVERY` (10 мин), после `GIVE_UP_AFTER` (48 ч) — `expired`.
  `check_payment` — одна проверка (её же зовёт кнопка «✓ Я оплатил(а)»;
  `expired` она тоже проверяет). Переход счёта в `completed`/`failed` —
  атомарный `UPDATE … WHERE status IN pending`: проход и кнопка не
  обработают одну оплату дважды. Оплата сессии → `_settle_booking`: холд жив
  — `finalize_booking`; холд истёк — подтверждение, только если слот всё ещё
  в `free_slots()`, иначе `paid_conflict` и Лане «свяжись: другое время или
  возврат» (Google недоступен — тоже конфликт). Запись уже обработана
  (двойная оплата) — Лане «лишняя оплата». Курс/игра — клиенту «доступ
  придёт на email», Лане «покупка». Экран счёта после оплаты удаляется
  (`Payment.message_id`), чтобы не заплатить второй раз.
- `database.py` — модели (`User` (+ `email` для счетов lava.top,
  `health_consent_at`), `Lead`,
  `Booking`, `Payment` (счёт lava.top: продукт, `booking_id` для сессии,
  `invoice_id`, статус, `waiver_at`, `checked_at` для расписания опроса), `Setting`,
  `Event`) и
  подключение. Схема создаётся через `create_all` при старте (создаёт только
  отсутствующие таблицы, колонки в существующих не меняет). Поверх этого
  `init_db` на Postgres идемпотентно доводит схему списком `_MIGRATIONS`
  (`ALTER TABLE … ADD COLUMN IF NOT EXISTS ...` для полей переноса и
  `users.email`; новая таблица `payments` создаётся самим `create_all`) —
  для добавления новых колонок ручной `DROP TABLE` не нужен, только когда
  меняется тип/состав колонок несовместимо. На sqlite (тесты) миграции не
  нужны — `create_all` сразу создаёт таблицу по актуальным моделям.
- `followup.py` — дожим: пользователь открыл экран консультации и за час не
  оставил заявку/не выбрал слот → один раз приходит «могу ли чем-то помочь?».
  Работает поверх таблицы `events` (переживает рестарты), окно 48 часов,
  повторно не шлёт (маркер — событие `followup_sent`).
- `middlewares.py`:
  - `CallbackSafetyMiddleware` — всегда шлёт `callback.answer()` в `finally`
    и гасит `TelegramBadRequest: message is not modified`.
  - `EventLoggingMiddleware` — пишет каждое нажатие/команду в таблицу `events`.
  - `CommandCleanupMiddleware` — на любую команду (`/…`) зовёт
    `ui.clear_screen`: текущее «окно» чата убирается, чтобы приветствие/раздел
    не оставались висеть под ответом команды.
- `filters.py` — `IsAdmin` (сверяет `from_user.id` с `admin_ids`).
- `booking_config.py` — читает из env расписание (`WORK_TIMES`,
  `WORK_WEEKDAYS`), горизонт/лид-тайм/холд (`BOOKING_HORIZON_DAYS`,
  `BOOKING_LEAD_HOURS`, `BOOKING_HOLD_MINUTES`) и таймзону в один
  frozen-датакласс `BookingConfig`, прокидывается в polling как workflow
  data (`booking_config: BookingConfig` в хендлерах).
- `google_calendar.py` — `GoogleCalendar`: `busy()` (freebusy-запрос по двум
  календарям — рабочему `CALENDAR_ID_BOOKINGS` и личному
  `CALENDAR_ID_PERSONAL`), `create_event()` / `delete_event()` в
  `CALENDAR_ID_BOOKINGS`. `GoogleCalendar.from_env()` читает
  `GOOGLE_SA_CREDENTIALS` (путь к JSON-файлу или сам JSON строкой),
  прокидывается в polling как `gcal: GoogleCalendar`.
- `slots.py` — чистая функция `free_slots(now, busy, holds, ...)`: считает
  свободные слоты по расписанию `BookingConfig` минус занятость Google
  минус активные холды в БД. Без побочных эффектов, легко тестируется.
- `formatting.py` — `format_slot_human()` (слот в Праге + Мск, день недели),
  `PRICE_TEXT` (цена консультации — витрина, сумму счёта задаёт оффер
  lava.top).
- `ui.py` — хелперы гигиены сообщений, на них держится вся уборка переписки
  в handlers/: `delete_safe(bot, chat_id, message_id)` — удалить сообщение,
  глотая `TelegramAPIError` (старше 48ч, уже удалено, нет прав);
  `edit_screen(bot, chat_id, message_id, text, reply_markup=None)` —
  отредактировать «экран» тем же способом, глотая «not modified» /
  «message to edit not found». Оба — no-op при ошибке, вызывающему коду не
  нужно оборачивать их в try/except. Плюс «единое окно на чат»: id текущего
  экрана хранится в таблице `settings` (`key=screen:<chat_id>`, через
  `get_setting`/`set_setting`/`del_setting`) — **не** in-memory, чтобы трекинг
  пережил рестарт (Railway передеплаивает часто; при in-memory состоянии
  `/start` и «В меню» после рестарта не могли удалить прежнее приветствие →
  дубликаты в чате):
  - `show_screen(bot, chat_id, text, reply_markup=None)` — **основной** способ:
    удаляет прежнее окно и шлёт новое сообщение, запоминая его. Так нажатие
    любой нижней кнопки/раздела убирает предыдущий экран (приветствие
    «исчезает», а не копится). `reply_markup` здесь — только inline-клавиатура
    экрана (или None).
  - `reset_keyboard(bot, chat_id, keyboard)` — держит нижнюю клавиатуру на
    **отдельном сообщении-якоре** (`key=kb:<chat_id>`). Так надо, потому что
    сообщение с `ReplyKeyboardMarkup` нельзя ни перерисовать в раздел через
    `edit_message_text` (правка не срабатывает), ни удалить (удаление
    сообщения **убирает** нижнюю клавиатуру). Контентные окна навигация
    удаляет/пересоздаёт, а якорь — нет, поэтому 8 кнопок видны на всех
    экранах. Якорь — короткое сообщение (`ANCHOR_TEXT`), пересоздаётся на
    `/start` (в т.ч. если чат очищен и старый якорь пропал).
  - `clear_screen(bot, chat_id)` — удалить текущее окно и забыть его (зовётся
    из `CommandCleanupMiddleware` на любую команду и внутри `show_screen`).
  - `track_screen(chat_id, message)` — запомнить уже отправленное сообщение
    как текущее окно (для `open_calendar`/`open_my_bookings`, которые шлют его
    сами, а не через `show_screen`).
  Итог: любое верхнеуровневое переключение (разделы, `/start`, «В меню»,
  «Записаться»/«Мои записи») = удалить прежнее окно + отправить новое; внутренняя
  inline-навигация (Отзывы, вопросы теста, дни календаря) правит текущее окно
  на месте (`callback.message.edit_text` — обычные inline-сообщения правятся
  нормально). Оговорка: первый деплой этой схемы для уже открытых чатов —
  в `settings` ещё нет `screen:<id>`, поэтому приветствие, что «висело» до
  деплоя, разово не удалится (id старого сообщения неизвестен).
- `handlers/` — по одному роутеру на файл, собираются в `setup_routers()`;
  `reply_router` зарегистрирован **перед** `fallback_router`, но порядок
  между ними функционально не важен: `fallback.py` ловит только
  колбэки (`quiz_ans:*`, `quiz_back`), без единого message-хендлера, так что
  перехватить текст кнопок нижней клавиатуры он в принципе не может. Тексты
  кнопок безопасны сами по себе — за счёт `StateFilter(None)` + точного
  `F.text == "..."` в `reply.py` (см. ниже):
  - `admin.py` — `/broadcast`, `/admin`, `/cancel`, `/bookings`
    (список ближайших `pay_claimed`/`confirmed` записей), подтверждение
    (`confirm_pay:<id>`, здесь же создаётся событие в календаре) и
    отклонение (`reject_pay:<id>`) оплаты, подтверждение (`resched_ok:<id>`)
    и отклонение (`resched_no:<id>`) переноса записи. После каждого действия
    карточка-уведомление у Ланы схлопывается в короткую итоговую строку
    (`callback.message.edit_text("✅ … — оплата подтверждена")` и т.п.) —
    вместо того чтобы оставлять развёрнутое уведомление висеть в чате.
    Роутер целиком под `IsAdmin`.
  - `booking.py` — выбор дня/времени из реальных Google-слотов, холд слота в
    `bookings` на `BOOKING_HOLD_MINUTES`, экран оплаты (`pay_screen_text`,
    валюта → `handlers/payments.py`), `finalize_booking` (общий для
    автоподтверждения и ручного `cb_confirm_pay`), легаси «Я оплатил(а)»,
    лимит активных записей (`MAX_ACTIVE_BOOKINGS`), «Мои записи»
    (`my_bookings`) и перенос (`resched:<id>` → выбор нового слота →
    сразу или через согласие Ланы, `RESCHEDULE_THRESHOLD`). Экраны записи
    вынесены в переиспользуемые функции `open_calendar(message, gcal, cfg,
    *, send)` и `open_my_bookings(message, tg_id, *, send)` — `send=True`
    шлёт новым сообщением (зовёт `handlers/reply.py` из нижней клавиатуры),
    `send=False` редактирует переданное `message` (зовут inline-колбэки).
    Перенос <24ч использует паттерн «якорь»: id сообщения с вопросом о
    причине сохраняется в FSM (`resched_screen_id`), а хендлер
    `RescheduleForm.reason` при ответе клиента удаляет его текст
    (`delete_safe`) и редактирует тот же якорь (`edit_screen`) — один экран
    вместо цепочки сообщений «спроси → ответь → спасибо».
  - `payments.py` — оплата через lava.top для сессии, курса и игры:
    `lava_pay:<product>:<RUB|EUR>:<booking_id>` (product `session`/`course`/
    `game`, booking_id > 0 только у сессии — whitelist + проверка, что бронь
    своя и холд жив) → подтверждения (оферта п. 7.2.1, ст. 9 GDPR), каждое
    отдельной кнопкой `lava_ok:<health|waiver>:…`: согласие на сведения о
    состоянии — один раз для сессии и курса (`User.health_consent_at`),
    просьба начать до истечения 14 дней — под каждый заказ (FSM-данные
    `waivers`, ключ `<product>:<booking_id>`, живёт `CONSENT_TTL` = 1 ч,
    при счёте копируется в `Payment.waiver_at`; поэтому FSM в этом модуле
    сбрасывается `set_state(None)`, а не `clear()`). Без подтверждений счёт
    не выставляется — проверка ещё и в `_issue_invoice`. После оплаты
    клиенту — подтверждение договора со временем согласия
    (`payments.contract_note`). Дальше → email из `User.email` или FSM `PayForm.email`
    (паттерн «якорь», как причина переноса: id экрана в FSM, ответ клиента
    удаляется, экран правится на месте; пока ждём email, текст кнопок нижней
    клавиатуры — тоже «ввод», как и в переносе: отказ «не похоже на email» и
    «⇦ Отмена») → `create_invoice` → `Payment` + экран счёта
    (`lava_invoice_kb`: «Оплатить N ₽» ссылкой, «✓ Я оплатил(а)» →
    `lava_check:<payment_id>`, «Изменить email» → `lava_email:…`, «⇦ Назад»
    → `lava_back:<product>:<booking_id>`). Выставленный счёт заново
    отсчитывает холд — оплата на стороне lava.top занимает минуты.
  - `fallback.py` — ловит колбэки старого квиза (`quiz_ans:*`, `quiz_back`),
    оставшиеся в сообщениях после рестарта бота и сброса FSM меню.
  - `lead.py` — FSM-заявка (имя → запрос → контакт), уведомление админам.
  - `start.py` — `/start`, `/id`, возврат в главное меню. `/start` ставит
    нижнюю клавиатуру якорем (`reset_keyboard(main_reply_kb())`) и шлёт
    приветствие обычным контентным окном через `show_screen()` (без нижней
    клавиатуры на нём); inline-меню на `/start` больше нет, пришпиливает
    пользователя в БД. Приветствие создаётся **только** на `/start`. Колбэк
    `start_menu` («В меню»/«Назад» из под-экранов) идёт через `show_screen()` —
    убирает текущий экран и показывает приветствие новым сообщением (единое
    окно: предыдущее исчезает, а не дублируется; клавиатура держится на якоре). `MAIN_MENU_TEXT` — без декоративной
    шапки `○─── ☾ ───○` и без строки «Быстрые действия». Payload `/start`
    разбирается ровно один: `course` (deep link `?start=course` с карточки
    курса на лендинге) — после якоря клавиатуры вместо приветствия сразу
    экран курса (`COURSE_TEXT` + `course_kb()`). Любой другой payload, в т.ч.
    `site` у остальных кнопок лендинга, — обычное приветствие.
  - `reply.py` — хендлеры нижней клавиатуры (`keyboards/reply.py`), 8 кнопок:
    разделы «О личной работе» / «Игра VECHNOST» / «Курс-практикум «Взломай
    Реальность»» / «Бесплатный Telegram-канал» / «Тест…» / «Задать вопрос
    Лане» → соответствующий контентный экран через
    `show_screen()` (удалить прежнее окно + отправить новое; тексты и
    клавиатуры переиспользуются из `consultation.py`/`info.py`/`quiz_data.py`);
    «Мои записи» → `open_my_bookings(..., send=True)`, «Записаться на сессию» →
    `open_calendar(..., send=True)` (обе + `clear_screen` до и `track_screen`
    после). Каждый хендлер сперва удаляет сообщение с текстом кнопки
    (`delete_safe`). Нижняя клавиатура переживает удаление сообщения (уровень
    чата), поэтому 8 кнопок видны во всех разделах. Все фильтруются
    `StateFilter(None)` (`F.text == BTN_*`) — не перехватывают текст, пока
    пользователь в какой-то FSM-форме (например, вводит причину переноса).
    Кнопки «Меню» больше нет.
  - `consultation.py`, `info.py` — контентные экраны (тексты + клавиатуры).
    В `info.py` же `COURSE_TEXT` — курс-практикум «Взломай Реальность» (тот
    же текст, что в карточке курса на лендинге; правишь один — правь и
    другой), и `GAME_TEXT`. Цены `COURSE_PRICE_TEXT`/`GAME_PRICE_TEXT` —
    витрина офферов lava.top. Курс и игра оплачиваются счётом lava.top
    (`course_kb()`/`game_kb()`: «Оплатить в рублях / в евро»); доступ
    lava.top присылает на email сам, бот только сообщает Лане о покупке.
    На сайте кнопок оплаты нет — только ссылки в бота.
- `keyboards/inline.py` — все inline-клавиатуры и внешние URL (одним блоком
  сверху), включая `LEGAL_*_URL` — три Google Docs Ланы в форме
  `/preview` (read-only читалка вместо редактора `/edit`; id собираются
  через `_GDOC.format(...)`). Источник у этих текстов один: копий в
  репозитории нет, футер лендинга ссылается на те же три документа.
  Лана правит документ — правка сразу видна и в боте, и на сайте.
  Ссылок на оплату здесь нет: у каждого счёта lava.top ссылка своя и
  приходит из API.
  `main_menu_kb()` удалён — разделы переехали в нижнюю клавиатуру.
- `keyboards/reply.py` — `main_reply_kb()`: постоянная `ReplyKeyboardMarkup`
  (`resize_keyboard=True`, `is_persistent=True`) на 8 кнопок (без цветных
  эмодзи, тексты совпадают с заголовками экранов) — константы `BTN_PERSONAL`
  (О личной работе), `BTN_GAME` (Игра VECHNOST), `BTN_COURSE` (Курс-практикум
  «Взломай Реальность», отдельным рядом на всю ширину сразу под первым —
  в два столбца длинную подпись обрезало бы), `BTN_CHANNEL` (Бесплатный
  Telegram-канал), `BTN_QUIZ` (Тест «Кто управляет твоей жизнью?»), `BTN_MY`
  (Мои записи), `BTN_ASK` (Задать вопрос Лане), `BTN_BOOK` (Записаться на
  сессию, растянут на всю ширину нижним рядом). Раскладка — 2 колонки,
  кроме рядов курса и записи (по одной кнопке).

## Флоу записи на слот (booking)

`Записаться` → бот дёргает `GoogleCalendar.busy()` по обоим календарям и
считает `slots.free_slots()` (будни по `WORK_TIMES`, минус занятость, минус
занятые слоты в БД, минус `BOOKING_LEAD_HOURS`/`BOOKING_HORIZON_DAYS`) →
выбор дня → выбор времени → перед вставкой проверяется лимит
`MAX_ACTIVE_BOOKINGS = 5` активных записей клиента (`_active_booking_count`:
`held` неистёкшие + `pay_claimed`/`confirmed` в будущем) → слот **держится**
за клиентом: `Booking(status="held", held_until=now+BOOKING_HOLD_MINUTES)`
(никакого события в календаре ещё нет) → экран оплаты (`pay_screen_text`:
`PRICE_TEXT`, юр-блок `LEGAL_NOTICE` со ссылками на оферту/политику/согласие,
шлётся с `link_preview_options` `is_disabled=True`, иначе карточка документа
ломает вёрстку; кнопки «Оплатить в рублях / в евро») → `handlers/payments.py`:
email (один раз, дальше из `User.email`) → счёт lava.top, холд отсчитывается
заново → клиент платит на стороне lava.top → `payments.py` видит
`completed` (фоновый опрос или кнопка «✓ Я оплатил(а)») → `finalize_booking`:
атомарно `held → confirmed` (с `calendar_sync_failed=True`, пока события
нет — так слот остаётся занятым для `_occupied_slots`), `gcal.create_event()`,
клиенту «Вы оплатили, спасибо…» (`BOOKING_CONFIRMED_TEXT`), Лане —
уведомление; `create_event()` упал — `calendar_sync_failed` остаётся `True`,
Лане «оформи вручную», статус всё равно `confirmed`. Заплатили после
истечения холда, а слот заняли — `paid_conflict` (см. `payments.py`).

Легаси до lava.top: `pay_claimed` — клиент нажал «✓ Я оплатил(а)»
(`paid:<id>` / `paid_crypto:<id>` — `_claim_payment`) на экране, открытом
ещё с Tribute/USDT. Экраны с такими кнопками могут висеть в чатах, деньги
могли уйти — путь сохранён: Лана подтверждает (`cb_confirm_pay` →
`finalize_booking` из `pay_claimed`) или отклоняет (`cb_reject_pay`, status
`cancelled`; событие удалять не нужно, т.к. оно ещё не создавалось на этом
статусе — `delete_event()` вызывается только если `google_event_id` уже был
проставлен), клиенту «оплату не нашли, слот освобождён». Кнопки
крипто-экрана (`pay_crypto:`, `pay_back:`) отвечают алертом «криптовалютой
больше недоступна». `pay_claimed` по-прежнему считается занятым и активным.

**Мои записи / перенос.** «Мои записи» (`my_bookings`) — список будущих
`pay_claimed`/`confirmed` записей клиента, у каждой кнопка «Перенести»
(`resched:<id>`) → тот же календарь свободных слотов (`_render_calendar` с
`prefix="resched"`) → выбор дня/времени. Если до исходного `slot_start`
ещё ≥ `RESCHEDULE_THRESHOLD` (`timedelta(hours=24)`) — перенос применяется
сразу через `apply_reschedule()` (для записи с уже созданным событием —
`delete_event()` старого + `create_event()` нового, `slot_start` меняется).
Если осталось < 24ч — бот просит причину (FSM `RescheduleForm.reason`), при
этом вопрос о причине остаётся единственным сообщением-«якорем» (id
сохранён в `resched_screen_id`): ответ клиента удаляется (`delete_safe`), а
сам якорь редактируется (`edit_screen`) вместо того, чтобы плодить новую
переписку. Дальше бот ставит
`Booking.reschedule_to/reschedule_reason/reschedule_status="pending"`,
админам приходят кнопки «✅ Подтвердить перенос» (`resched_ok:<id>`) /
«❌ Отклонить перенос» (`resched_no:<id>`). Approve — перепроверяет, что
`reschedule_to` всё ещё в `free_slots()`; если свободен — двигает через
`apply_reschedule()` и чистит поля переноса; если уже заняли — оставляет
запись на старом слоте, поля переноса тоже чистятся, клиенту и админу
сообщение «слот заняли, перенос не выполнен». Reject (`resched_no`) —
**отменяет саму запись** (`status="cancelled"`, `delete_event()` если
событие уже было), оплата не возвращается, клиенту сообщение «перенос
отклонён, запись отменена, оплата не возвращается».

Просроченные холды (`held`, `held_until` в прошлом) никто явно не чистит —
они просто перестают попадать в `free_slots()`/`_occupied_slots()` и не
мешают новым бронированиям; фоновой задачи-уборщика нет (лениво, по
конструкции). Google недоступен на любом из шагов (показ слотов/дней,
бронирование, оплата, перенос) → пользователю понятный текст + кнопка
«Попробовать снова» / «Написать в ЛС», не мёртвая кнопка.

Гонка «два клиента бронируют
один и тот же слот одновременно» подавляется проверкой «слот всё ещё в
`free_slots()`» перед вставкой, но не UNIQUE-констрейнтом на уровне БД —
для объёма этого бота риск принят как есть. Та же проверка «слот ещё
свободен» защищает и перенос — как самостоятельный (`cb_resched_slot`),
так и подтверждаемый Ланой (`cb_resched_ok`).

## Конвенции

- Хендлеры колбэков **не вызывают** `callback.answer()` вручную — это делает
  `CallbackSafetyMiddleware`. Исключение: ответ с текстом/алертом
  (`callback.answer("…", show_alert=True)`) — можно, повторный пустой answer
  от middleware подавляется.
- Фильтруй колбэки через `F.data == "..."`, а не `lambda` (единообразие).
- `callback_data` с параметром — через двоеточие: `lead_start:consultation`,
  `book_slot:2026-07-21:14:00`, `paid:5`. Разбор — `split(":", n)`, значения
  валидировать (whitelist / диапазон / принадлежность записи пользователю).
- Переименовал колбэк, который уже ушёл пользователям в старых сообщениях? —
  оставь алиас (`F.data.in_({"new", "old"})`), пример: `booking_start` +
  legacy `consultation_pay`.
- Любой пользовательский текст, попадающий в HTML-сообщение (уведомления
  админам), экранируй через `aiogram.html.quote(...)` — `parse_mode=HTML`
  включён глобально.
- Тексты сообщений — модульные константы (`UPPER_SNAKE`) рядом с хендлером.
- Декоративная типографика: символы `✦ ☾ ⇨ ●` в заголовках. Старую шапку-
  разделитель `○─── ☾ ───○` со всех экранов убрали — новые тексты её не
  добавляют. Цветные эмодзи на кнопках не используем (осознанное решение
  владельца).

## Подводные камни

- **Бот не может писать первым.** Уведомления о заявках/бронях и рассылка
  доходят только до тех, кто нажал `/start` у бота. Новый админ обязан открыть
  бота и нажать `/start`, иначе уведомления ему не придут.
- **Приватные ссылки на канал** (`t.me/c/...`) открываются только у подписчиков —
  канал отдаётся кнопкой-ссылкой на экране «Бесплатный Telegram-канал».
- Рассылка `/broadcast` использует `copy_message` — работает с **любым** типом
  контента (текст, фото, видео, голосовые, кружки), без пометки «переслано».
  После доставки каждому пользователю бот пересобирает низ чата
  (`_restore_bottom`: `reset_keyboard` + `show_screen(MAIN_MENU_TEXT)`) — иначе
  сообщение Ланы падает ПОД 🤍-якорь клавиатуры и старое окно; нужно наоборот,
  чтобы оно оказалось над сердечком, а меню осталось внизу. Побочный эффект
  принят: если клиент читал раздел, вместо него он увидит приветствие.
- **Живучесть рассылки.** На человека уходит 5 запросов (копия + якорь +
  приветствие и два удаления), а лимит Telegram — ~30 запросов в секунду на
  бота, и удаления в него тоже считаются. Поэтому пауза между получателями —
  `BROADCAST_DELAY = 0.4` (было 0.15 → ~33 запроса/с, flood control 429 и
  потерянные получатели). `_copy_to` делает до `SEND_ATTEMPTS = 4` попыток,
  честно выжидая `TelegramRetryAfter.retry_after`, и возвращает статус
  `sent`/`blocked`/`error`: `TelegramForbiddenError`/`TelegramNotFound` —
  человек заблокировал бота или удалился, повторять бессмысленно. Тело цикла
  и `_restore_bottom` ловят `Exception` целиком (в `_restore_bottom` есть
  обращения к `settings`, и ошибка БД раньше валила всю рассылку через
  `dp.errors()` — часть людей оставалась без сообщения, а Лана не видела даже
  итогового отчёта). Отчёт админу теперь разделяет доставлено / заблокировали /
  ошибки и печатает до 10 telegram_id с ошибкой; прогресс обновляется каждые
  `PROGRESS_EVERY = 25` получателей. Кнопки превью, пережившие рестарт, ловит
  `cb_broadcast_stale` (тот же `broadcast_confirm`/`broadcast_cancel`, но без
  фильтра по состоянию): FSM хранится в памяти, после рестарта хендлер со
  `StateFilter` не срабатывает и кнопка раньше молча ничего не делала. Чего
  по-прежнему нет: рассылка живёт в памяти процесса — рестарт Railway посреди
  цикла обрывает её без возможности продолжить.
- **lava.top.** Ключ — `LAVA_API_KEY` в переменных Railway (без него бот
  работает, но оплата недоступна). Цена — в двух местах: оффер в кабинете
  lava.top (сколько реально спишут) и тексты (`PRICE_TEXT`,
  `COURSE_PRICE_TEXT`, `GAME_PRICE_TEXT` + сайт). Поменяли цену в lava.top —
  поменяй тексты; `test_prices_match_bot` сверяет сайт с ботом, но до
  lava.top тесты не дотягиваются. Новый продукт в кабинете — новый id
  оффера в `lava.OFFERS`. Email клиентов теперь хранится в `users.email` —
  это персональные данные, политика конфиденциальности должна это
  упоминать.
- `zoneinfo("Europe/Prague")` требует пакет `tzdata` (есть в requirements) —
  без него упадёт на Windows и в slim-образах.
- Каждый новый `callback_data` в клавиатуре должен иметь хендлер — иначе кнопка
  молча ничего не делает.
- Сравнение дат из БД: sqlite отдаёт наивные datetime, postgres — aware.
  В `followup.py` есть `_as_utc()` — используй его при сравнениях.

## Проверка изменений

```bash
python -m py_compile main.py database.py middlewares.py filters.py followup.py slots.py google_calendar.py booking_config.py formatting.py lava.py payments.py ui.py handlers/*.py keyboards/*.py
```

Автотесты есть (`tests/`, pytest) — гоняют хендлеры через фейковую сессию
(`BaseSession` с подменённым `make_request`) на `sqlite+aiosqlite:///:memory:`
и `dp.feed_update()`, плюс юнит-тесты чистых функций (`slots.free_slots`,
`formatting.format_slot_human`, `booking_config.load`). Так проверялись
FSM-заявка, бронирование слотов из Google-занятости, холд/оплата/отклонение,
дожим, напоминание за 24ч и рассылка. Важно: workflow data в тесте задаётся
`dp["admin_ids"] = [...]`, `dp["booking_config"] = ...`, `dp["gcal"] = ...`
(или фейковый `GoogleCalendar`), `dp["lava"] = FakeLava()` (счета в памяти,
статус двигает тест: `lava.statuses[invoice_id] = "completed"`, затем
`payments.payments_pass(...)`), FSM-ключ — пара (chat, user), поэтому у
фейковых колбэков chat должен быть личкой пользователя. Прогон:
`PYTHONIOENCODING=utf-8 python -m pytest -q`. На Windows-консоли обязательно
с `PYTHONIOENCODING=utf-8`, иначе падает на кириллице в выводе.
