# Уборка сообщений бота + постоянная нижняя клавиатура

Дата: 2026-07-27

## Цель

Две UX-правки, едут одним заходом:

1. **Бот прибирает за собой** — FSM-потоки (заявка, причина переноса) схлопываются
   в одно редактируемое сообщение; текстовые ответы клиента удаляются;
   уведомления Ланы после действия сворачиваются в одну строку.
2. **Постоянная нижняя клавиатура** (ReplyKeyboard) с быстрыми действиями:
   📅 Записаться · 📋 Мои записи · 🏠 Меню · 💬 Вопрос Лане.

Проблема (со скриншотов клиентского чата): FSM-диалоги шлют новое сообщение на
каждом шаге, плюс висят текстовые ответы клиента и повторные промпты. Навигация
по меню/календарю уже чистая (там `edit_text`).

## Решения (зафиксированы с заказчиком)

| Тема | Решение |
|---|---|
| FSM-потоки клиента | Одно «якорное» сообщение, редактируется на каждом шаге |
| Текстовые ответы клиента | Удаляются после прочтения (`message.delete()`) |
| Уведомления Ланы после действия | Сворачиваются в одну строку (не дописывание к полному тексту) |
| Нижняя клавиатура | ReplyKeyboard: Записаться, Мои записи, Меню, Вопрос Лане |
| `/start` | Одно сообщение: приветствие **с нижней клавиатурой**; богатое меню открывается кнопкой «🏠 Меню» |
| Меню команд «/» (setMyCommands) | **Вне объёма** — не выбрано |
| Глобальный трекинг «текущего экрана» | **Вне объёма** (YAGNI) |
| Схлопывание «принято» + «спасибо» в оплате | **Вне объёма** — 2 сообщения на бронь, не спам |

## Механизм уборки

### Хелперы (новый модуль `ui.py`)

```
async def delete_safe(bot, chat_id, message_id) -> None
    # bot.delete_message, глотает TelegramBadRequest/TelegramAPIError
    # (сообщение старше 48ч, уже удалено, нет прав) — никогда не падает

async def edit_screen(bot, chat_id, message_id, text, reply_markup=None) -> None
    # bot.edit_message_text, глотает «message is not modified» и «message to edit not found»
```

Оба чистые обёртки над Bot API, тестируются с фейковой сессией.

### Якорь FSM-потока

При старте потока в FSM-данные кладётся `screen_id` — id сообщения-экрана
(для callback-входа это `callback.message.message_id`, т.к. `edit_text` не меняет
id). На каждом текстовом шаге:
1. `await message.delete()` — удалить текст клиента (обёрнуть в try/except).
2. `edit_screen(bot, chat_id, screen_id, next_text, next_kb)` — обновить якорь.

Если `screen_id` отсутствует (поток начат до правки / потерян) — фолбэк на обычный
`message.answer(...)`, без падения.

## Клиентские потоки

### Заявка (`handlers/lead.py`) — ВНЕ ОБЪЁМА

В PR #8 кнопка «Оставить заявку» убрана из меню и дожима, поток заявки в UI
недоступен. Уборку `lead.py` не делаем — оставляем как есть (код на месте, но
не достижим). Если позже вернём заявку в UI — тогда и применим тот же паттерн
якоря.

### Причина переноса (`handlers/booking.py`) — единственный FSM-поток к уборке

- Промпт «напиши причину» уже ставится через `callback.message.edit_text` в
  `cb_resched_slot` (<24ч ветка) — это якорь; сохранить `screen_id` в FSM там же.
- `resched_reason` (текст): удалить текст-причину; `edit_screen` якоря на
  «Запрос на перенос отправлен Лане». Команда на «/» (выход) — тоже редактирует
  якорь в «Ок, перенос отменён» и удаляет текст.

## Сворачивание уведомлений Ланы

Сейчас `cb_confirm_pay` / `cb_reject_pay` / `cb_resched_ok` / `cb_resched_no`
делают `edit_text(полный_текст + "\n\n✅ …")`. Меняем на **короткую итоговую
строку** (кнопки уже убираются). Примеры:

- confirm_pay → `✅ <имя/id> · <слот> — оплата подтверждена`
- reject_pay → `❌ <слот> — оплата отклонена, слот освобождён`
- resched_ok → `✅ <слот> — перенос подтверждён`
- resched_no → `❌ перенос отклонён, запись отменена`

Данные (имя/слот) уже есть в хендлере. `format_slot_human` для слота.

## Нижняя клавиатура

### Клавиатура (`keyboards/inline.py` или новый `keyboards/reply.py`)

```
def main_reply_kb() -> ReplyKeyboardMarkup:
    # resize_keyboard=True, is_persistent=True
    # ряд 1: 📅 Записаться | 📋 Мои записи
    # ряд 2: 🏠 Меню       | 💬 Вопрос Лане
```

### Установка

`/start` (`handlers/start.py`): приветствие отправляется с `reply_markup=
main_reply_kb()` (нижний бар). Богатое inline-меню (О личной работе / VECHNOST /
канал / тест) открывается кнопкой «🏠 Меню».

### Хендлеры текста кнопок (`handlers/start.py` или `reply.py`)

Reply-кнопки шлют **текст**. На каждый — message-хендлер (матч по точному тексту,
`F.text == "📅 Записаться"` и т.д.), который:
1. Удаляет сообщение-нажатие (`message.delete()`, через `delete_safe`).
2. Показывает целевой экран **новым** сообщением:
   - 📅 Записаться → экран календаря записи (как `cb_booking_start`).
   - 📋 Мои записи → список записей (как `cb_my_bookings`).
   - 🏠 Меню → главное inline-меню (как `cb_start_menu`, но новым сообщением).
   - 💬 Вопрос Лане → короткое сообщение с inline-кнопкой «Написать в ЛС» (URL
     на личку эксперта).

Чтобы не дублировать логику, вынести тело показа календаря/списка в функции,
переиспользуемые и callback-хендлером, и reply-хендлером (напр. существующие
`_load_free`/`_render_calendar` уже есть; для «Мои записи» — общая функция
рендера списка). Reply-хендлеры **не** в FSM-состоянии, поэтому не должны
перехватывать текст во время заявки/переноса: ставятся с фильтром «нет активного
состояния» (`StateFilter(None)`), либо reply-роутер регистрируется так, чтобы
FSM-хендлеры (в состоянии) срабатывали первыми.

### Важный порядок фильтрации

FSM-хендлеры заявки/переноса матчат `F.text` в своём состоянии. Reply-кнопки тоже
текст. Чтобы нажатие «📅 Записаться» во время ввода имени не улетало в имя —
reply-текст-хендлеры фильтруются `StateFilter(None)` (срабатывают только вне
потоков). Внутри потока reply-кнопки трактуются как обычный текст шага (или можно
их там игнорировать — MVP: трактуются как текст, т.е. пользователь сам виноват;
приемлемо, порог низкий).

## Обработка ошибок

- Все `delete`/`edit` — через `delete_safe`/`edit_screen`, глотают
  `TelegramBadRequest`/`TelegramAPIError`. Сообщение >48ч → удаление молча
  не сработает, поток продолжается.
- Потерянный `screen_id` (редеплой в середине потока) → фолбэк на `answer`.

## Тестирование

Фейковая сессия логирует `DeleteMessage`/`EditMessageText`/`SendMessage`.
- Заявка целиком: считаем `SendMessage` в чат клиента — должно быть ≤1 нового
  (остальное — `EditMessageText` якоря); тексты клиента → есть `DeleteMessage`.
- Причина переноса: `resched_reason` не шлёт новое `SendMessage` клиенту
  (редактирует якорь); текст-причина удалён.
- Уведомление Ланы после confirm — итоговый `edit_text` короткий (проверить, что
  не содержит полного исходного текста, содержит «подтверждена»).
- Нижняя клавиатура: `/start` отправляет сообщение с `ReplyKeyboardMarkup`
  (4 кнопки). Нажатие «📅 Записаться» (текст) → удаляет нажатие + показывает
  календарь. То же для «Мои записи», «Меню», «Вопрос Лане».
- `delete_safe`/`edit_screen` не падают на ошибке API (юнит с бросающей сессией).

Прогон: `PYTHONIOENCODING=utf-8 python -m pytest -q`; компиляция всех модулей.

## Вне объёма

- setMyCommands (меню «/»).
- Глобальный менеджер «текущего экрана» для устранения следов reply-прыжков.
- Схлопывание оплатного «принято» + «спасибо» в одно сообщение (хранение id брони).
