# Запись на консультацию через Google Calendar + попутные фиксы

Дата: 2026-07-26

## Цель

Переделать запись на консультацию так, чтобы:

1. **Расписанием управляла Лана**, а не хардкод в коде. Разовую занятость она
   закрывает событием в своём календаре — слот сразу пропадает из бота.
2. **Календарь занимали только оплатившие.** Между «выбрал время» и «оплатил»
   настоящая бронь не создаётся — только временный холд, который сам истекает.
   Мусорные брони и захват всего расписания одним человеком становятся невозможны.
3. **Сессии автоматически попадали в календарь Ланы** (синхронизация, которой
   сейчас нет вообще: `SLOT_TIMES` и «пн–пт» захардкожены в `booking.py`).
4. Заодно закрыть блокеры 1–5, 7, 8, 9, 12 из ревью бота от 2026-07-26.

Оплата остаётся на Tribute с ручным подтверждением Ланой — это не меняется
(другой платёжки нет, вебхуков Tribute не шлёт).

## Почему Google Calendar, а не Calendly / Cal.com

Рассмотрены и отклонены:

- **Calendly** — вебхуки и Scheduling API только на платных тарифах; оплату берёт
  лишь через Stripe/PayPal (для рублёвой аудитории неприменимо). Отклонён.
- **Cal.com** — бесплатный тариф с API и вебхуками подошёл бы, есть штатный
  `POST /v2/slots/reservations` (холд слота, по умолчанию 5 мин, настраивается).
  Но требует email участника при создании брони (в Telegram его нет) и вводит
  между ботом и календарём Ланы лишнего вендора.
- **Google Calendar напрямую** — выбран. Событию не нужен email участника (имя
  клиента кладём в заголовок/описание). Лана управляет доступностью тем
  календарём, которым уже пользуется, — синхронизировать нечего, это и есть её
  календарь. `freebusy.query` — read-only, безопасен для чужого календаря.
  Ни подписки, ни чужого API.

Цена решения: резервирование слота, отмену/перенос и напоминания пишем сами
(Cal.com дал бы из коробки). Это ~100 строк, которые в Telegram-части всё равно
понадобились бы (напоминания шлём в Telegram, не на email).

## Решения (зафиксированы с заказчиком)

| Тема | Решение |
|---|---|
| Порядок шагов | Клиент **выбирает конкретное время до оплаты**, затем платит за него |
| Удержание слота | Штатного холда нет (пишем свой) — холд в нашей БД на **30 минут** |
| Что показываем до оплаты | Реальные свободные времена на **30 дней** вперёд из Google Calendar |
| Источник правды по занятости | Google Calendar (`freebusy`), не наша таблица |
| Доступ к календарю | **Service account** + Лана расшаривает календарь с правом «Вносить изменения» |
| Структура календарей | Отдельный календарь **«Консультации»** (бот пишет туда) + **личный на чтение** |
| Email клиента | Не спрашиваем. В событие кладём имя и Telegram-ник |
| Google Meet | Пробуем автосоздание ссылки; не выйдет из-за ограничений service account — Лана шлёт ссылку вручную, как сейчас (не регресс) |
| Рабочие окна | Остаются в конфиге (пн–пт, 12:00/14:00/16:00 Прага). Правка окон навсегда — админ-команда, **второй этап** |
| Миграция | Не нужна — живых броней нет, таблицу `bookings` пересоздаём под новую схему |
| Блокеры 1–5,7,8,9,12 | Чиним в этот же заход |
| Длина кнопок теста, сохранение результата теста | **Вне объёма** — это решения из спека 2026-07-26, отдельный разговор |

## Архитектура

Три новых/переработанных модуля, разделённых по ответственности, каждый
тестируется изолированно.

### `google_calendar.py` — тонкий клиент Google (единственное место с HTTP к Google)

```
busy(start, end)            -> list[tuple[datetime, datetime]]   # freebusy.query по двум календарям
create_event(slot, client) -> str  (event_id)                    # events.insert в «Консультации»
delete_event(event_id)      -> None                              # events.delete
```

- Бизнес-логики внутри нет — только вызовы Google API и разбор ответа.
- Тестируется с подставным транспортом (как `FakeSession` в текущих проверках).
- Авторизация: service account через `google-auth` + `google-api-python-client`.
  Ключ сервис-аккаунта — в env как JSON или путь к файлу.
- Читает занятость из **двух** календарей: «Консультации»
  (`CALENDAR_ID_BOOKINGS`) и личного (`CALENDAR_ID_PERSONAL`), объединяя интервалы.

### `slots.py` — чистая функция расчёта доступности (без I/O)

```
free_slots(now, busy, holds, windows, horizon_days, lead_time) -> list[datetime]
```

- `windows` — рабочие окна (пн–пт, времена из конфига).
- `busy` — занятые интервалы из Google (передаются снаружи, функция не ходит в сеть).
- `holds` — активные холды из нашей БД (`held_until > now`).
- `lead_time` — буфер перед сессией (нельзя записаться менее чем за N часов) → блокер 7.
- Свободно = окна − busy − holds − (прошлое + lead_time).
- Сердце фичи. Полностью покрывается таблицей кейсов без сети и БД.

### `handlers/booking.py` — тонкий UI поверх `slots.py` и `google_calendar.py`

- Уезжают: `SLOT_TIMES`, `HORIZON_DAYS`, `available_days()`, `free_times()`,
  `_future_times()` — расписание больше не в коде.
- Остаются: клавиатуры дней/времён (переиспользуются почти как есть), экран
  оплаты, обработка «Я оплатил(а)».
- Добавляется: обработка истёкшего холда, ошибок Google, лимит 1 активная бронь.

### Таблица `bookings` (пересоздаётся)

| Поле | Назначение |
|---|---|
| `id`, `telegram_id`, `slot_start` (datetime, UTC), `status`, `created_at` | как сейчас, `slot_date`+`slot_time` → единый `slot_start` |
| `held_until` (datetime, nullable) | до какого момента слот держится за клиентом |
| `google_event_id` (str, nullable) | id события в календаре «Консультации» |
| `calendar_sync_failed` (bool, default false) | Google лёг в момент оплаты — Лане чинить руками |

Статусы: `held` → `pay_claimed` → `confirmed` / `cancelled`.
(Старый `new` уходит: слот теперь либо held, либо уже оплачен.)

### Новые env-переменные

```
GOOGLE_SA_CREDENTIALS   — JSON service account (или путь к файлу)
CALENDAR_ID_BOOKINGS    — id календаря «Консультации» (бот пишет сюда)
CALENDAR_ID_PERSONAL    — id личного календаря Ланы (только чтение занятости)
BOOKING_HOLD_MINUTES=30
BOOKING_HORIZON_DAYS=30
BOOKING_LEAD_HOURS=3    — буфер перед сессией
WORK_TIMES=12:00,14:00,16:00
WORK_WEEKDAYS=0,1,2,3,4 — пн–пт
```

## Поток данных и статусы

```
«Записаться»
   → google_calendar.busy(now, now+30д)
   → slots.free_slots(...) → кнопки дней → кнопки времён
время выбрано
   → проверка лимита (нет ли уже активной held/pay_claimed брони у этого telegram_id)
   → INSERT booking status=held, held_until = now + 30 мин
   → экран оплаты Tribute (₽/€), текст: «Время держим до 14:35 (Прага)»
«✓ Я оплатил(а)»
   → перепроверка: слот всё ещё свободен в Google И холд наш И не истёк
   → google_calendar.create_event() → google_event_id
   → status=pay_claimed
   → уведомление Лане: [✅ Подтвердить оплату] [❌ Оплата не найдена]
Лана ✅
   → status=confirmed → клиенту подтверждение (день/время в двух поясах)
Лана ❌
   → google_calendar.delete_event() → status=cancelled
   → клиенту: «Оплату не нашли, напиши в ЛС»
холд истёк (не оплатил)
   → held_until в прошлом → slots.free_slots перестаёт его учитывать.
     Строку не удаляем и не чистим фоново — ленивая проверка в запросе.
```

Ключевое: настоящая бронь (событие в календаре) создаётся **только после
«Я оплатил(а)»**. Передумавший на экране оплаты не оставляет следа в календаре.

## Обработка ошибок (три случая, которые нельзя проглотить)

1. **Google недоступен на экране выбора слота.**
   Не показываем пустой/битый список. Сообщение «расписание временно недоступно,
   напиши в ЛС» + кнопки [Написать в ЛС] [Попробовать снова]. Никогда молчаливого
   `return` (сегодня в боте 4 таких мёртвых кнопки — блокер 4 в booking).

2. **Холд истёк между выбором и нажатием «Я оплатил(а)», слот увели.**
   Перепроверка перед `create_event`. Если время занято: честно сообщить,
   предложить выбрать другое, **и уведомить Лану** (клиент мог уже заплатить в
   Tribute на это время — нужно ручное разрешение).

3. **Google лёг в момент «Я оплатил(а)».**
   Факт оплаты фиксируем: `status=pay_claimed`, `calendar_sync_failed=true`.
   Лане в уведомление добавляем «⚠️ не удалось создать событие, оформи вручную».
   Оплата не теряется никогда.

## Попутные фиксы (блокеры из ревью 2026-07-26)

| № | Блокер | Фикс |
|---|---|---|
| 1 | Цена 111 €/11111 ₽ на экране оплаты vs 100 €/10000 ₽ на витрине | Единая константа `PRICE_TEXT` = «100 € / 10000 ₽», используется в обоих местах |
| 2,3 | Брошенная бронь блокирует слот навсегда; один человек забирает весь календарь | Растворяются архитектурой: холд с TTL + Google как источник правды + лимит 1 активная бронь на `telegram_id` |
| 4 | После редеплоя `quiz_ans:`/`quiz_back`/lead-FSM без состояния — мёртвые кнопки | Catch-all хендлеры без фильтра состояния → «сессия сброшена, начни заново» + кнопка в меню |
| 5 | У Ланы нет обзора броней; уведомление может потеряться молча | Команда `/bookings` (список ближайших) + если `send_message` Лане упал, писать в лог **и** дублировать всем админам |
| 7 | Запись за минуту до сессии | `BOOKING_LEAD_HOURS` в `slots.free_slots` |
| 8 | «CET» летом неверно; аудитория считает в МСК | Время в двух поясах: «12:00 Прага (14:00 Мск)», корректный CEST через `zoneinfo` |
| 9 | На экране результата теста нет кнопки записи | Добавить «Записаться» в `quiz_result_kb` |
| 12 | Нет напоминания перед сессией | Напоминание клиенту за сутки — в существующий `followup_loop` (там уже есть цикл и работа с `events`) |

**Вне объёма (осознанно):** длина кнопок теста (60 кнопок по 48–106 символов) и
сохранение результата теста в БД — это зафиксированные решения спека
2026-07-26, меняются отдельным разговором с заказчиком.

## Тестирование

- `slots.py` — таблица кейсов: пустой календарь; busy перекрывает окно; холд
  занимает слот; истёкший холд игнорируется; lead_time отсекает ближайшее;
  выходные исключены; горизонт 30 дней.
- `google_calendar.py` — подставной транспорт: разбор `freebusy`, объединение
  двух календарей, `create_event`/`delete_event`.
- Хендлеры — фейковая Telegram-сессия + sqlite in-memory + `dp.feed_update()`
  (стенд, которым проверялся бот в ревью). Обязательные сценарии:
  - Google недоступен на выборе слота → корректное сообщение, не мёртвая кнопка.
  - Холд истёк между выбором и оплатой → перепроверка ловит, Лана уведомлена.
  - Двойной клик «Я оплатил(а)» → одна бронь, одно событие в календаре.
  - Отмена Ланой → `delete_event`, слот снова свободен в `free_slots`.
  - Лимит: вторая попытка брони при активной первой → отказ с пояснением.
- Обязательно `PYTHONIOENCODING=utf-8` на Windows-консоли.

## Развёртывание

- Новые зависимости: `google-auth`, `google-api-python-client`.
- Лана: создаёт календарь «Консультации», расшаривает **оба** календаря
  service-аккаунту (личный — «Просматривать все данные», «Консультации» —
  «Вносить изменения»). Пошаговая инструкция — в README при реализации.
- Railway: добавить env-переменные. HTTP-сервер под вебхуки **не нужен** —
  бот сам создаёт события, polling остаётся.
- `create_all` не мигрирует существующие таблицы. Живых броней нет → таблицу
  `bookings` дропнуть и пересоздать (разово, вручную или скриптом на старте).

## Второй этап (вне этого спека)

- Вебхуки/пуш-уведомления Google, чтобы ловить правки, сделанные мимо бота
  (Лана удалила событие руками → снять бронь у клиента).
- Админ-команда управления рабочими окнами (сдвинуть 12/14/16 без редеплоя).
- Перенос брони клиентом из бота.
