# Перенос записи, лимит 5, событие в календаре только после подтверждения

Дата: 2026-07-27

## Цель

Три доработки поверх записи на консультацию (после PR #5 и #6):

1. **Событие в Google создаётся только после подтверждения оплаты Ланой**, а не в
   момент «Я оплатил(а)».
2. **Лимит активных записей на клиента: 1 → 5.**
3. **Перенос записи клиентом:** ≥24ч до сессии — самостоятельно; <24ч — только с
   согласия Ланы, с указанием причины; при отказе Ланы запись отменяется без
   возврата оплаты.

Заодно навсегда убираем грабли «на новой колонке дропни таблицу руками»:
`init_db` получает идемпотентную авто-миграцию недостающих колонок.

## Решения (зафиксированы с заказчиком)

| Тема | Решение |
|---|---|
| Событие в календаре | Создаётся на `confirm_pay` (подтверждение Ланой), не на `paid` |
| Занятость слота между paid и confirm | Слот держат `held`(не истёкшие) + `pay_claimed`; confirmed — через событие в Google |
| Лимит записей | ≥5 активных → отказ («у тебя уже 5 записей») |
| Порог самостоятельного переноса | 24 часа до `slot_start` |
| Перенос <24ч, отклонён Ланой | Запись **отменяется**, слот освобождается, **оплата не возвращается** |
| Точка входа клиента | Кнопка **«Мои записи»** в главном меню |
| Причина переноса | Спрашиваем у клиента только в ветке <24ч (FSM-ввод текста) |
| Миграция новых полей | Идемпотентный `ALTER TABLE … ADD COLUMN IF NOT EXISTS` в `init_db` (Postgres) |
| Отмена записи клиентом | **Вне объёма** (YAGNI) — просили перенос, не отмену |

## Изменение модели `Booking`

Добавляются три поля (все nullable):

| Поле | Тип | Назначение |
|---|---|---|
| `reschedule_to` | `DateTime(timezone=True)` | Запрошенный новый слот (только пока `pending`) |
| `reschedule_reason` | `String(500)` | Причина переноса (ветка <24ч) |
| `reschedule_status` | `String(20)` | `pending` пока ждём Лану; иначе пусто/None |

Статусы `Booking.status` без изменений: `held → pay_claimed → confirmed / cancelled`.
Поля переноса живут поверх и очищаются после применения/отклонения.

### Миграция

`init_db` после `create_all`: если диалект `postgresql`, выполнить для каждой новой
колонки `ALTER TABLE bookings ADD COLUMN IF NOT EXISTS <col> <type>`. Postgres
поддерживает `IF NOT EXISTS` — идемпотентно, безопасно на каждом старте. Для sqlite
(тесты, in-memory) `create_all` создаёт полную схему сразу, ALTER не нужен и не
запускается. Это устраняет прежнюю необходимость ручного `DROP TABLE` при смене схемы.

## Занятость слотов (ключевой инвариант фичи 1)

Событие в календаре теперь появляется только на `confirm`. Значит слот `pay_claimed`
(оплачен, ждёт подтверждения) в Google ещё не занят. Чтобы его не увели:

```
занято = Google busy (freebusy)                       # confirmed — здесь
       + slot_start брони со status='held' и held_until > now
       + slot_start брони со status='pay_claimed'
```

Функция `_active_holds` в `handlers/booking.py` переименовывается в `_occupied_slots`
и возвращает `slot_start` всех `held`(не истёкших) и `pay_claimed` броней. Она
передаётся в `slots.free_slots(..., holds=...)` — сигнатура `free_slots` не меняется
(тот же список «занятых начал слотов»).

## Поток: событие на confirm (фича 1)

```
«✓ Я оплатил(а)» (cb_paid)
  → проверка held + владелец
  → status = pay_claimed   (событие НЕ создаём, google_event_id = None)
  → уведомление Лане: [✅ Подтвердить оплату] [❌ Оплата не найдена]

Лана ✅ (cb_confirm_pay)  — только из pay_claimed
  → create_event() в календаре «Консультации»
  → при успехе: status=confirmed, google_event_id=…, calendar_sync_failed=False
  → при ошибке Google: status=confirmed, calendar_sync_failed=True,
    Лане «⚠️ событие не создалось, оформи вручную»
  → клиенту подтверждение

Лана ❌ (cb_reject_pay)   — только из pay_claimed/held
  → события ещё нет (google_event_id None) → удалять нечего
  → status=cancelled, клиенту «оплату не нашли, слот освобождён»
```

`calendar_sync_failed` логика переезжает из `cb_paid` в `cb_confirm_pay`.

## Лимит 5 (фича 2)

`_user_has_active(session, tg_id, now) -> bool` заменяется на
`_active_booking_count(session, tg_id, now) -> int` — считает активные записи
пользователя (будущие `pay_claimed`/`confirmed` + непросроченные `held`). В
`cb_book_slot` перед созданием холда: если count ≥ 5 → алерт
«У тебя уже 5 активных записей 🤍 Заверши или перенеси одну из них.» и стоп.

## Перенос (фича 3)

### Клиентский экран «Мои записи»

- Новая кнопка в `main_menu_kb`: «Мои записи» (callback `my_bookings`).
- `cb_my_bookings`: список будущих `pay_claimed`/`confirmed` броней клиента. Пусто →
  «У тебя пока нет активных записей». Иначе на каждую — строка с
  `format_slot_human(slot)` и кнопка «Перенести <дата>» (callback `resched:<id>`).
  Плюс «⇦ В меню».

### Выбор нового слота

- `cb_resched_start` (`resched:<id>`): проверка, что бронь принадлежит клиенту и
  активна. Запоминаем в FSM `booking_id`. Показываем **тот же календарь**
  (`booking_calendar_kb` / `_render_calendar`) — но callback дней помечаем как
  перенос, чтобы не спутать с новой записью. Для этого вводим отдельный префикс:
  дни в режиме переноса → `resched_day:<iso>`, времена → `resched_slot:<utc-iso>`.
  (Календарь и клавиатура времени параметризуются префиксом callback.)
- Клиент выбирает день → время. Новый слот обязан быть свободен (проверка через
  `free_slots`), иначе алерт «это время только что заняли».

### Развилка 24 часа

`now` (UTC) против `slot_start` **исходной** брони:

- **`slot_start - now >= 24ч` (самостоятельно):**
  - `confirmed` с `google_event_id` → `delete_event(старое)`; `create_event(новое)`;
    при ошибке Google → `calendar_sync_failed=True`, Лане предупреждение, но перенос
    применяется (slot_start обновлён).
  - `pay_claimed` (события ещё нет) → просто `slot_start = новый`.
  - Клиенту «✦ Перенесено на <new>». Лане инфо-уведомление (без кнопок).
- **`slot_start - now < 24ч` (нужна Лана):**
  - FSM: спрашиваем причину → сохраняем `reschedule_to=новый`,
    `reschedule_reason=текст`, `reschedule_status='pending'`. Исходная бронь пока
    без изменений (старый слот держится).
  - Лане уведомление: старый слот, новый слот, причина, кнопки
    **[✅ Подтвердить перенос] [❌ Отклонить перенос]** (`resched_ok:<id>` /
    `resched_no:<id>`).

### Решение Ланы (только для pending)

- **✅ `cb_resched_ok`:** перепроверяем, что `reschedule_to` всё ещё свободен. Если
  занят → Лане «новый слот уже занят, перенос невозможен», pending снимаем, бронь
  остаётся на старом слоте, клиенту сообщение. Если свободен → применяем как в
  ветке ≥24ч (двигаем событие/слот на `reschedule_to`), чистим поля переноса,
  клиенту «✦ Перенос подтверждён на <new>».
- **❌ `cb_resched_no`:** запись **отменяется** — `delete_event` если есть,
  `status=cancelled`, поля переноса очищаются, слот освобождается. Клиенту:
  «Перенос отклонён. К сожалению, запись отменена, оплата не возвращается 🤍».

### Занятость и pending-перенос

Пока перенос `pending`, новый слот **не** резервируется отдельно (низкий поток —
принятый компромисс, как и гонка двойной брони). На approve перепроверяем занятость
нового слота; если увели — перенос не проходит, бронь остаётся на старом слоте.

## Обработка ошибок

- Google недоступен при переносе (нужно двигать событие) → как в остальном booking:
  понятный текст + кнопка, перенос не применяется, состояние не портится.
- Кривой callback (`resched:*`, `resched_slot:*`) → алерт «не понял, начни заново»,
  без молчаливого `return`.
- Потерянный FSM причины после редеплоя → catch-all (как блокер 4) или мягкий сброс.

## Тестирование

- `_occupied_slots` включает `pay_claimed` (слот держится между paid и confirm).
- Событие создаётся на `confirm`, не на `paid` (FakeGCal.events пуст после paid,
  непуст после confirm).
- Reject из `pay_claimed` не зовёт `create_event`/`delete_event` (события нет).
- Лимит: 5 активных → шестая бронь отклонена алертом.
- «Мои записи»: показывает будущие оплаченные, у каждой кнопка `resched:<id>`.
- Перенос ≥24ч (confirmed): старое событие удалено, новое создано, `slot_start` новый.
- Перенос ≥24ч (pay_claimed): `slot_start` новый, событий Google не трогали.
- Перенос <24ч: `reschedule_status=pending`, причина сохранена, Лане ушли кнопки.
- Approve: слот/событие двинулись, поля переноса очищены.
- Reject: `status=cancelled`, событие удалено (если было), клиент уведомлён о
  невозврате, слот снова свободен в `free_slots`.
- Approve, когда новый слот уже занят → перенос не применён, бронь на старом слоте.
- Миграция: `ALTER … ADD COLUMN IF NOT EXISTS` идемпотентен (для sqlite не запускается,
  схема полная; юнит на диалект-ветку).

Прогон: `PYTHONIOENCODING=utf-8 python -m pytest -q`, компиляция всех модулей.

## Вне объёма

- Отмена записи клиентом отдельной кнопкой.
- Резервирование нового слота на время pending-переноса.
- Возвраты/refund-логика (политика — «не возвращается», без денежных операций в боте).
